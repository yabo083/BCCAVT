# ADR-0004: 阅读器顶层顺序 = 取回顺序（渲染层只追加，禁止按时间重排）

## 日期
2026-10-14

## 状态
accepted（修订 [ADR-0003](0003-reader-infinite-scroll.md) 的渲染顺序一节）

## 背景
ADR-0003 已经保证**取数**只追加（游标状态机：`next === null` 才到底、失败保留游标、`commit` 只追加不重排）。但**渲染**把这份顺序又改了一遍：

- 顶层分页走 B 站 `mode=2`（按时间），平台返回的顺序是**时间倒序**（每页首条 `is_begin`/最新，整页都比上一页更旧）；
- 展示层统一取 `buildForest(comments).roots`，而 `buildForest` 把根评论按 `createdAt` **升序**排序（`src/core/tree.ts#buildForest`）。

两条拼起来 = **每取一页，这一页的行被整块排到已读内容之上**。

真机实测（同一构建、同一视频、同一批真实响应、同一滚动脚本；探针装在宿主帧与嵌入帧两个 world，见「证据」）：

| 指标（每次取数） | 修复前 | 修复后 |
|---|---|---|
| 新行插到旧行之前（`insertedAbove`） | 21 / 33 / 30 / 30 | **0 / 0 / 0 / 0** |
| 旧行下标被动过（`movedOld`） | 21 / 52 / 85 | **0 / 0 / 0** |
| 阅读器文档 layout-shift 累计值 | **1.92**（源=行元素位移） | **0.06**（源=页脚下方位移 + 挂载首帧） |
| 列表前 3 行的身份 | 每取一页就换 | 全程不变 |
| 内容高度 | 2858→6136→9973→13223→**13199（窗口滑动回收了尾部行）** | 2858→6136→9973→13223（单调） |

用户的感受是「加载新评论时被打回刚看过的位置」：**视口 `scrollY` 一动不动**（宿主文档只变高、槽位高度单调不减），但内容在视口内整体下移一页高（≈3300px），于是同一屏幕坐标上换成了更早看过的评论。

## 决策
**渲染顺序 = 取回顺序**（`mergeComments` 的插入顺序 = 平台游标顺序），森林只负责层级：

- `src/ui/EmbeddedComments.vue`：`merged` 派生自 `mergeComments(pagerState.items, ...loaded, added)`；`roots` 按 `merged` 的顺序取 `forest.byId`，**不再用 `forest.roots`**；父评论缺失的孤儿（森林会提升为根）按森林顺序补在末尾，保证「渲染集合 = 森林的根集合」，不丢行。
- 森林内的兄弟顺序（楼中楼按时间升序）**不变**——那条链本来就只在本页内追加，且符合「回复按时间读」的直觉。
- `src/core/tree.ts#buildForest` 的排序**保留**：工作台/图谱/快照要的是与来源无关的稳定顺序。

配套：`READER_NAVIGATION` 只在**目标身份**真的变化时才重置（见 ADR-0003 的 2026-10-14 补充），否则一次 URL 抖动会丢掉全部已读页并把槽位打回 360px —— 那是同一类「回弹」里唯一真正的宿主文档缩高路径。

## 依据（关键外部事实）
- **平台顺序**：`x/v2/reply/wbi/main?mode=2` 按时间倒序返回，游标 `pagination_reply.next_offset` 继续取更旧的页；实测 6 页、每页 20 条，页间 ctime 严格分离（页 1 最旧 1791747484 > 页 2 最新 1791745773）。
- **CLS 语义**：Layout Instability API 的 `layout-shift` 条目按「不稳定元素在视口内的位移面积」计权（<https://web.dev/articles/cls>）。实测修复前的条目源就是 `article.comment-row` / `div.thread-lines`（行元素），修复后行元素不再出现，只剩列表下方 `div.more`（页脚被追加内容推下，单次 ≤0.023）。
- **不要靠浏览器补偿**：宿主侧 scroll anchoring 在本场景双重失效（anchor node 只能是 iframe 盒子；写 `height` 命中 SANACLAP 抑制表），见 ADR-0003「依据」。
- **参考工程口径**：长列表的位移成本来自「在用户阅读位置之上出现未预留空间的动态内容」，对策是把动态内容放在阅读位置**之下**（追加）并预留空间，而不是事后补偿滚动位置（Addy Osmani, *Infinite Scroll without Layout Shifts*, <https://addyosmani.com/blog/infinite-scroll-without-layout-shifts/>）。

## 后果
- 正面：取一页 = 纯尾部追加，已渲染行的下标与几何全程不变（`rowCap` 窗口不再滑动回收尾部行，`v-for` 只做插入）；「加载新评论」不再把用户打回上面；`scrollY`/`scrollHeight`/槽位高度的单调性由 ADR-0003 继续保证。
- 阅读顺序：列表从**最新**往旧读（与平台顺序、与「滚到底继续取更旧的」一致）；置顶评论仍由适配器在首屏插到最前，会话内新写的顶层评论仍由 `pinned` 钉在最上面。
- 负面 / 代价：`roots` 不再等于 `forest.roots`（多一次 `byId` 查表）；同一条评论若同时落在两页（平台异常），按先到位置渲染，不与 `createdAt` 二次对齐——这是**有意的**：渲染只信游标顺序，任何二次排序都会重新引入「插入到已读内容之上」。
- 遗留：页脚 `div.more` 仍会被追加内容推下（修复后单次 ≤0.023，只在取数落定帧可见）；阅读器挂载首帧有一次 0.026 的头部微移（与本次问题无关，属「加载与空/错误态」待办）。

## 备选方案（关键）
- **把 `buildForest` 改成按 `createdAt` 降序**：对当前平台数据等价，但仍把渲染顺序押在「时间字段单调」这个外部假设上；一旦平台改序、出现同秒并列或被服务端重排，渲染层会再次重排已读内容。取回顺序不依赖任何外部排序假设（**追加即正确**），也少一次排序。
- **插入前记锚点、插入后由宿主修 `scrollTop`**（roadmap 原方案）：差值只能在嵌入页算、滚动只能宿主做，需要新增跨文档桥消息与一次强制回流；而且它只是把「内容下移」换成「用户被滚回去」——用户仍然看到内容跳动，只是方向相反。**先做到不移动，再谈补偿**。
- **靠 `overflow-anchor` / 浏览器 scroll anchoring**：跨源 iframe 场景已证无效（ADR-0003「依据」）。

## 补充（2026-10-29：排序切换）
阅读器新增「最热 | 最新」分段切换（`EmbeddedComments.vue#switchOrder`，默认最热与原生一致）。
换序是**换数据集**而非客户端重排：中断旧序在途页、`pager.reset()` 回到游标起点、按新序
（`CrawlOptions.order`，页键含 order 维度）重新取第一页——已渲染行在切换瞬间整体替换，
本 ADR 约束的是「同一序内的行序永不动」，整批换数据集不在这条契约之内（用户主动操作、
一次性结构变化，走结构性缩高上报）。切换回旧序由页缓存直接命中（order 在键里），零回源。
